## 1. Серый текст в поле ввода, которого никто не писал {#1}

**Симптом.** В чате Клона внизу, в поле ввода, стоит осмысленная фраза вроде
«Да, делай в work/check-planned, в main не сливай». Выглядит как набранное
и неотправленное сообщение. Возникает вопрос: кто это написал и почему не отправил.

**Причина.** Это **подсказка Claude Code** — готовый ответ в один клик.
Интерфейс рисует её поверх пустого поля. В разметке это
`div.truncate.text-muted` в наложенном слое, а само поле при этом пустое.

**Что делать.** Ничего. Это не сообщение, его никто не писал. Если хочешь
убедиться — прочитай значение поля:

```js
const el = document.querySelector('[role="textbox"].ProseMirror');
(el.value ?? el.innerText ?? '').trim().length   // 0 — значит поле пустое
```

**Чего не делать.** Не отправлять эту строку, не разобравшись. Она не твоя,
и её формулировка может не совпадать с тем, что ты собирался сказать.

*Напоролись дважды за час 08.10.2026, оба раза гадали заново.*

## 2. Кириллица пропадает при отправке сообщения Клону {#2}

**Симптом.** Отправил Клону русский текст — он получил
`" , . : , , text. , . . , , . ."`. Знаки препинания и латиница на месте,
русских букв нет.

**Причина.** Поле ввода в Claude Code — редактор **ProseMirror**. Синтетические
нажатия клавиш (`computer` → `type`) он обрабатывает с потерей кириллицы.
Дело не в длине текста и не в случайном сбое: воспроизводится стабильно.

**Решение.** Вставлять текст целиком, как из буфера обмена:

```js
const el = document.querySelector('[role="textbox"].ProseMirror');
el.focus();
document.execCommand('selectAll', false, null);
document.execCommand('delete', false, null);
document.execCommand('insertText', false, 'текст сообщения');
```

Затем прочитать `el.innerText`, убедиться, что кириллица на месте, и только
потом нажимать Enter. После отправки — перечитать переписку и найти в ней
своё сообщение, **по правилам из грабель 12**: наивная проверка врёт.

*08.10.2026. Первый раз списали на случайность, второй раз поймали на живом.*

## 12. Проверил, что сообщение ушло, — а оно не ушло {#12}

**Симптом.** После Enter проверяю: текст на странице есть, значит отправлено.
На самом деле Клон ничего не получил, а текст всё это время лежал в поле ввода.

**Причина, две сразу.**

Первая: между вставкой текста и нажатием Enter фокус может уйти с поля ввода —
страница живая, в ней что-то дорисовывается. Enter тогда приходится по кнопке,
на которой оказался фокус, и ничего не отправляет.

Вторая, и она опаснее: **поле ввода — часть страницы.** Проверка вида
`document.body.innerText.includes('кусок сообщения')` находит собственный текст
в неотправленном поле и радостно отвечает «да, дошло». То есть проверка
подтверждает отправку ровно в том случае, когда отправки не было.

**Решение.** Проверять два условия вместе, и оба обязательны:

```js
const el = document.querySelector('[role="textbox"].ProseMirror');
el.innerText.trim().length === 0          // поле опустело — значит ушло
document.body.innerText.split(кусок).length - 1 === 1  // и текст ровно один раз
```

Пока текст в поле, совпадение на странице будет, но оно своё же. Пустое поле —
единственный надёжный признак отправки.

Если Enter не сработал, вернуть фокус и повторить:

```js
el.focus();
const s = window.getSelection(), r = document.createRange();
r.selectNodeContents(el); r.collapse(false);
s.removeAllRanges(); s.addRange(r);
```

Текст при этом уже в поле — набирать заново не надо, иначе уйдёт дважды.

как это стало граблями. Была права.*

## 4. Сборка падает на `configure-pages` {#4}

**Симптом.** Девять запусков подряд, все красные, всегда один шаг:
`Run actions/configure-pages@v5`.

**Причина.** GitHub Pages на репозитории не был включён. Шаг с
`enablement: true` пытается включить его сам и не может: токену сборки
такого права не выдают на репозитории, где Pages ни разу не настраивали.

**Решение.** Один раз руками: **Settings → Pages → Source: GitHub Actions**.
После этого `enablement` не нужен, шаг просто подхватывает готовый Pages.

**Чего не делать.** Не искать ошибку в workflow и не чинить YAML — он исправен.

## 5. По адресу открывается старый сайт {#5}

**Симптом.** DNS переключены на GitHub, сборка зелёная, а браузер показывает
прежний сайт.

**Причина.** Кэш резолвера на стороне смотрящего. Разные машины видят разное:
из контейнера домен уже указывал на GitHub, у владельца — ещё на старый хостинг.

**Как проверить, а не гадать.** Посмотреть, кто отвечает:

```js
const r = await fetch('/robots.txt?cb=' + Date.now(), {cache: 'no-store'});
r.headers.get('server')   // "GitHub.com" — новый, "nginx/…" — старый
```

**Решение.** Подождать, либо сбросить кэш: `chrome://net-internals/#dns` →
Clear host cache, либо открыть с другого канала — например, с телефона
по мобильному интернету.

## 6. Не читается собственный сайт {#6}

**Симптом.** Попытка прочитать страницу сайта через загрузчик возвращает
`ROBOTS_DISALLOWED`.

**Причина.** Мы сами закрыли сайт от роботов. Запрет распространяется на всех,

**Решение.** Смотреть через браузер. Так и будет до того шага плана, где мы
снимаем запреты (предпоследний, перед выпуском).

## 7. Не открывается прототип на Tilda {#7}

**Симптом.** `eon_rus.tilda.ws` не читается обычной загрузкой страницы.

**Причина.** Закрыт в `robots.txt`.

**Решение.** Только браузер, расширение. Текст снимается оттуда и кладётся
в задание Клону целиком: у него браузера нет.

**Адреса страниц угадывать бесполезно.** Они не совпадают с названиями пунктов
меню: «Скиф» лежит на `/skif_opisanie`, а `/skif` отдаёт 404. Корень
`eon_rus.tilda.ws/` расширение открывать отказывается («Navigation to this domain
is not allowed»), хотя подстраницы открывает, — поэтому пройти по меню с главной
тоже не выйдет. `sitemap.xml` пуст: сайт закрыт от индексации.

Поэтому: 404 на угаданном адресе — **сразу спросить Ирину**, а не перебирать
написания. Она отвечает ссылкой за минуту, перебор занимает десять и чаще всего
ничего не находит. Спрашивать лучше про все оставшиеся страницы разом.

## 8. Логи упавшей сборки не скачиваются {#8}

**Симптом.** Выгрузка логов GitHub Actions не проходит, а `unzip` ругается:
`Attempt to add a non-ASCII file name`.

**Две разные причины, обе были.**

Первая: имена шагов workflow по-русски. Архив логов называет файлы по именам
шагов, и `unzip` спотыкается о кириллицу. **Решение:** имена шагов писать
латиницей; распаковывать питоном (`zipfile`), а не `unzip`.

Вторая: сама выгрузка закрыта прокси — отдаёт `Forbidden`. **Решение:** его нет.
Какой шаг упал, видно через API (`/actions/runs/<id>/jobs`), а текст ошибки —
нет. Если шаг не опознаётся по названию, проверять гипотезы другими способами
и говорить прямо, что лог прочитать не удалось.

## 9. Файлы из прошлой сессии исчезли {#9}

Ничего важного не оставлять только в рабочей папке.

## 9а. Репозиторий откатился к старому коммиту {#9a}

**Симптом.** `git log` показывает коммит, после которого было сделано ещё
полтора десятка. В `content/` восемь файлов вместо девятнадцати. При этом
`git status` чистый — как будто ничего и не делали. Ощущение, что работа
нескольких часов исчезла.

**Причина.** Контейнер сессии пересоздан, рабочая копия восстановлена
из старого снимка. Это та же девятая проблема, но коварнее: файлы не просто
пропали, а **подменились согласованным старым состоянием**. Ничто не выглядит
сломанным, поэтому можно спокойно начать работать поверх отката и затереть
новое старым.

**Решение.** Ничего не потеряно, если работа была запушена: сервер — настоящий
носитель, локальная копия одноразовая.

```sh
git fetch origin main
git reset --hard FETCH_HEAD      # рабочее дерево чистое, терять нечего
python3 build.py && python3 check.py
```

**Как заметить раньше.** Признак отката — расхождение между тем, что ты помнишь,
и тем, что в `git log`. Поэтому после любого перерыва в работе первым делом:

```sh
git log --oneline -1 && git ls-remote origin main
```

Если верхний коммит не совпадает с серверным — откат. Проверять это стоит
и после каждой потери памяти: сверка занимает секунду, а работа поверх отката
стоит часов.

**Чего не делать.** Не пушить с `--force` и не коммитить поверх, пока не сверился
с сервером. Откат локальный, на сервере всё цело — испортить можно только
своими руками.

хотя они были в main. Это и был признак — main оказался старым.*

## 10. Проверка позеленела, но ошибки остались {#10}

**Симптом.** `check.py` возвращает 0, хотя в выводе два десятка строк.

**Причина.** У проверки две степени тяжести. Ссылки на страницы из списка
`PLANNED` — предупреждения, сборку не валят. Всё остальное — ошибки.

**Важное, на чём обожглись.** Когда это разделение вводили, предупреждением
стала **любая** ссылка на несуществующую страницу — включая опечатку.
`guardain.html` проходил молча и терялся среди двадцати пяти жёлтых строк.
Смягчая шум, выключили сигнал.

**Правило на будущее.** Приглушая проверку, спроси: а что перестанет ловиться?
Приглушать надо не «похожие случаи», а именно те, что перечислены поимённо.

## 11. Файл на Google Drive не перезаписывается {#11}

**Симптом.** `update_file` отрабатывает, а содержимое файла прежнее.

**Причина.** `update_file` меняет только свойства файла — имя, расположение.
Содержимое им не заменить.

**Решение.** Создать новый файл с нужным содержимым, старый отправить в корзину.

## 13. Файл страницы пропал сам {#13}

**Симптом.** В `git status` висит `D content/skif.json`. Страницу никто не удалял,
последние полчаса шла совсем другая работа. Следом ломаются проверки, которые
до этого проходили, — и ломаются непонятно, потому что исходное состояние уже не то.

**Причина.** Скрипт контрольных поломок. Чтобы проверить случай «страница написана,
но осталась в списке ненаписанных», он **создавал** временный `content/skif.json`,
а после прогона удалял его. Когда скрипт писали, страницы «Скиф» не было. Потом
она появилась — и скрипт молча перезаписал настоящий файл пробным, а затем стёр.

Опасность не в самой потере: файл лежит в гите и возвращается одной командой.
Опасность в том, что **следующие проверки идут от испорченного исходного состояния**,
и их результатам верить нельзя, хотя выглядят они обычно.

**Решение.** Два правила для любого скрипта, который портит данные нарочно:

1. Временный файл в `content/` называть именем, которого в проекте **не может
   появиться**. Брать имя из `PLANNED` — не выход: оттуда имена как раз и переезжают
   в проект, в этом весь смысл списка. Лучше заведомо служебное,
   вроде `content/__проба__.json`.
2. Откат должен **возвращать прежнее содержимое**, а не удалять файл. Если файла
   не было — удалить; если был — положить обратно байт в байт. Разницу скрипт
   обязан знать сам, а не предполагать.

И общее: после прогона поломок смотреть `git status`. Чистое дерево — часть
результата проверки, а не формальность.

**Дополнение второе, в тот же день.** Скрипт, переделанный по правилу выше,
удалил `assets/img/.gitkeep`: он создавал папку `assets/img/` для пробных снимков,
а в откате сносил её целиком — исходя из того, что до него её не было. К тому
времени папку уже завели по-настоящему. Отсюда окончательная формулировка:
**откат удаляет не «папку для проб», а список того, что он сам создал.**
И отказывается работать, если файл с таким именем уже есть.

**Дополнение от 08.10.2026, после второго захода на те же грабли.** Скрипт,
переделанный по правилу 1, через неделю снова оказался опасен: он брал имя
из `PLANNED`, а страница с этим именем успела появиться. Вывод точнее:
**«точно несуществующее имя» устаревает вместе с проектом. Надёжен только
откат, который не знает имён** — отслеживаемые файлы вернуть из git,
неотслеживаемые в рабочей папке удалить. Тогда скрипт не нужно
перепроверять каждый раз, когда проект растёт.

## 14. Страница обновилась, а ведёт себя по-старому {#14}

**Симптом.** Выкатили новую версию, сборка зелёная, разметка на странице новая —
видно по новым полям. А работает страница по-старому: показывает прежние числа,
прежние надписи, как будто правки не было. Перезагрузка не помогает.

**Причина.** Браузер закешировал `style.css` или скрипт **по имени файла**.
Имя не менялось — значит, с его точки зрения, и файл не менялся. HTML он
перечитал, а стили и скрипты взял из кеша.

Поймали на калькуляторе: страница пришла с новым полем, а скрипт остался
вчерашний и считал по-старому. Самое неприятное — выглядит это не как ошибка
кеша, а как «правка не доехала» или «сломался расчёт», и искать начинаешь
совсем не там.

**Решение.** Сборка добавляет к адресу отпечаток содержимого:
`style.css?v=dbad3cd9`. Меняется файл — меняется отпечаток — браузер скачивает
заново. Не меняется — кеш работает, как и должен.

Для разовой проверки своими глазами хватит открыть адрес с любым хвостом:
`?v=` и текущее время.

и не ищет файл с вопросительным знаком в имени.*

## 15. `git fetch --all` молча не приносит ни одной ветки {#15}

**Симптом.** `git fetch --all --prune` отрабатывает без ошибок и печатает одну
строку про `main`. `git branch -r` показывает старый список. Вывод напрашивается
сам: Клон ничего не запушил, он ещё работает. На самом деле ветка на сервере
лежит уже полчаса.

**Причина.** У `origin` **пуст список `fetch`** — тот самый `+refs/heads/*:refs/remotes/origin/*`,
который обычно создаётся при клонировании. Проверить:

```sh
git config --get-all remote.origin.fetch   # ничего не вывел — вот оно
```

Без него `fetch --all` не знает, какие ссылки тянуть, и приносит только то,
что назвали в командной строке (`git fetch origin main`). Ошибки при этом нет:
команда сделала ровно то, о чём её попросили, — ничего.

**Решение.**

```sh
git config --add remote.origin.fetch '+refs/heads/*:refs/remotes/origin/*'
git fetch --all --prune
```

**Чем опасно.** Это единственные грабли, которые врут в ответ на правильный
вопрос. Проверка «появились ли новые ветки» — первый шаг приёмки работы, и здесь
она уверенно отвечает «нет». Поэтому в порядке проверки стоит сверять не только
`git branch -r`, но и сервер напрямую:

```sh
gh api repos/Irina-IP-26/eon-rus/branches --jq '.[].name'
git ls-remote --heads origin
```

Эти две команды спрашивают сервер и от локальных настроек не зависят.
