# Как сайт попадает на сервер

Сборка живёт на GitHub, сайт — на своём сервере с nginx. Каждый push в `main`
запускает `.github/workflows/deploy.yml`: он проверяет сайт, собирает его
и копирует каталог `dist/` на сервер по SSH.

**В этом файле нет ни адресов, ни ключей, ни паролей** — репозиторий публичный.
Всё это лежит в секретах репозитория на GitHub, куда заглянуть может только
владелец.

---

## Что нужно один раз настроить

Пять секретов в репозитории и отдельный пользователь на сервере. Порядок
действий ниже — по шагам, сверху вниз.

### Шаг 1. Пользователь для выкладки

Пользователь `deploy` на сервере уже есть (uid 1000). Создавать его не нужно,
нужно только дать ему его собственный каталог для ключей — при первой попытке
он был создан от имени root:

```sh
mkdir -p /home/deploy/.ssh
chown -R deploy:deploy /home/deploy/.ssh
chmod 700 /home/deploy/.ssh
```

### Шаг 2. Каталог сайта

Сайт еон.рус в nginx уже настроен отдельно: конфиг
`/etc/nginx/sites-enabled/xn--e1aqc.xn--p1acf`, каталог
**`/var/www/eon-rus/public`**. Сертификат Let's Encrypt для домена тоже
выпущен. Писать конфиг не нужно, нужно отдать каталог пользователю выкладки:

```sh
chown -R deploy:deploy /var/www/eon-rus/public
```

Рядом с сайтом в том же каталоге живёт `.well-known/acme-challenge` — через
него Let's Encrypt продлевает сертификат. Выкладка его не трогает и не удаляет,
это прописано в `deploy.yml` отдельным исключением.

Соседние сайты на том же сервере: `e-on.su`, `eve-battery.ru`,
`thundersky-winston.ru`, `winston-battery.ru`. Их каталоги выкладка не видит
и видеть не должна.

### Шаг 3. Сделать ключ доступа

На сервере, под root:

```sh
ssh-keygen -t ed25519 -C "github-deploy-eon" -f /root/eon_deploy -N ""
cat /root/eon_deploy.pub >> /home/deploy/.ssh/authorized_keys
chown -R deploy:deploy /home/deploy/.ssh
chmod 600 /home/deploy/.ssh/authorized_keys
```

Получилось два файла. `eon_deploy.pub` — открытая часть, она уже на месте.
`eon_deploy` — закрытая, её содержимое сейчас понадобится:

```sh
cat /root/eon_deploy
```

Этот текст (целиком, вместе со строками `-----BEGIN` и `-----END`) идёт
в секрет `DEPLOY_KEY`. После того как секрет заведён, файл с сервера стоит
удалить: `rm /root/eon_deploy`.

### Шаг 4. Снять отпечаток сервера

Чтобы GitHub при выкладке убеждался, что подключается именно к нашему серверу,
а не к кому-то, кто притворился им:

```sh
ssh-keyscan -t ed25519 ВАШ_АДРЕС_СЕРВЕРА
```

Вывод — одна строка. Она идёт в секрет `DEPLOY_KNOWN_HOSTS`.

### Шаг 5. Завести секреты на GitHub

Репозиторий `Irina-IP-26/eon-rus` → **Settings** → в левом столбце
**Secrets and variables** → **Actions** → кнопка **New repository secret**.
Пять штук, имена вводить точно:

| Имя секрета | Что положить |
|---|---|
| `DEPLOY_HOST` | адрес сервера — IP или имя |
| `DEPLOY_USER` | `deploy` |
| `DEPLOY_PATH` | каталог сайта из шага 2, без косой черты в конце |
| `DEPLOY_KEY` | содержимое закрытого ключа из шага 3, целиком |
| `DEPLOY_KNOWN_HOSTS` | строка из шага 4 |

Шестой, `DEPLOY_PORT`, нужен только если SSH на сервере слушает не 22-й порт.

## Как это работает дальше

Любое изменение, попавшее в `main`, само уезжает на сервер: проверка, сборка,
копирование, и в конце запрос к главной странице по адресу домена — если она
не ответила, выкладка считается неудачной и в GitHub загорается красный крест.

Копирование идёт с ключом `--delete`: файлов, которых больше нет в сборке,
не останется и на сервере. Поэтому **каталог в `DEPLOY_PATH` должен принадлежать
только этому сайту**. Если указать туда каталог с чем-то ещё, это «что-то ещё»
будет стёрто при первой же выкладке.

Сайт закрыт от поисковиков: `robots.txt` содержит `Disallow: /`, на каждой
странице стоит `noindex`. Снятие запрета — отдельный шаг перед выпуском,
он описан в `README.md`, и делается он не вместе с переездом.
