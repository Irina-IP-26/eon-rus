### 2. `.github/workflows/pages.yml` — полная история для дат

```yaml
      - uses: actions/checkout@v4
        with:
          fetch-depth: 0
```

`actions/checkout` по умолчанию берёт один последний коммит. В такой копии `git log -1 -- файл`
вернёт **дату этого коммита для всех страниц**. Получится та же ложь, от которой
вы предостерегали в задаче, только она выглядит честной. Поэтому `seo.py` сначала
спрашивает `git rev-parse --is-shallow-repository`. Если история неполная, даты в карте
не ставятся вовсе. Без `fetch-depth: 0` карта на живом сайте будет без дат. Это допустимо,
но жаль.

## Как устроено

### Адреса

- Главная — `https://<домен>/`, без `index.html`. Иначе у главной два адреса,
  и поисковик выбирает сам. Остальные — `https://<домен>/<страница>.html`, ровно как
  ссылки в меню.
- Кириллический домен записывается в форме для протоколов: `еон.рус` →
  `https://xn--e1aqc.xn--p1acf/`. Протокол карты сайта требует ASCII. Если сделать так же
  и в canonical, адрес будет одинаковым везде. Браузеры и поисковики показывают его
  по-русски. Проверял вызовом `seo.page_url("еон.рус", "index")`.
- `site.json` → `domain` может быть записан с `https://` или с `/` на конце — всё это
  срезается.

### Дата изменения

- Берётся как `git log -1 --format=%cs -- content/<страница>.json`, только дата `ГГГГ-ММ-ДД`.
  В задаче предлагался `%cI`, полная дата со временем. Время карте сайта ничего не даёт,
  а часовой пояс коммита — лишний повод для разнобоя. Протокол принимает оба варианта.
- Нет git, неполная история, файла ещё нет в истории — даты нет, сборка не падает.
- Ограничение: при локальной сборке с незакоммиченной правкой дата будет от прошлого
  коммита. На CI такого не бывает: там собирается коммит.
- Сейчас у всех 20 страниц дата `2026-10-08`. Это правда: вся история репозитория — сегодня
  (`git log --format=%cs -- content`, 34 коммита, все от 08.10).

### Картинка в карточке

Предусмотрена, как просили. `og_meta` ищет первый снимок страницы с непустым `src`,
обходя блоки по порядку: обычно это герой. Пустые слоты пропускаются. Если снимок найден,
добавляются:

- `og:image` с абсолютным адресом;
- `og:image:alt` из `alt`;
- `og:image:width` и `og:image:height` из самого файла, через `imgsize.py`;
- `twitter:card` становится `summary_large_image`.

Пока снимков нет, картинки в карточке нет, и ничего придумывать не нужно.

### `check.py`, обычный прогон

Проверяет то, что есть, и молчит о том, чего нет:

- `[адрес]`: canonical один, абсолютный, ведёт на эту же страницу (если на другую — пишет,
  на какую), у двух страниц не совпадает;
- `[карточка]`:
  - пять обязательных свойств на месте, свойства не повторяются (кроме `og:image*`);
  - `og:url` — адрес страницы;
  - `og:image` абсолютный, а если он на нашем домене — файл лежит в `dist/`;
- `[карта сайта]`:
  - XML читается, корень правильный;
  - каждая страница ровно один раз, лишних адресов нет, адреса абсолютные;
  - дата в формате и не в будущем;
  - строка `Sitemap:` в `robots.txt` ведёт на `https://<домен>/sitemap.xml`, и сама карта есть.

Это ошибки, а не предупреждения: неверный canonical хуже отсутствующего. Он прямо говорит
поисковику «настоящая страница — другая».

## Завязки на GitHub Pages

Искал по `build.py`, `check.py`, `seo.py`, `assets/`, `content/`, workflow, README.

1. **`build.py` пишет `dist/CNAME`** — настройка своего домена для GitHub Pages.
   На своём сервере файл просто будет лежать и откроется по адресу `/CNAME`, внутри только
   домен. Вреда нет, при переезде строку можно убрать.
2. **`build.py` пишет `dist/.nojekyll`** — просит GitHub не прогонять сайт через Jekyll.
   Чужому серверу всё равно. Скрытый файл: nginx по умолчанию его отдаст, но он пустой.
3. **`.github/workflows/pages.yml`** — публикация через `configure-pages` /
   `upload-pages-artifact` / `deploy-pages`. При переезде меняются шаги после `Build site`,
   на копирование `dist/` на сервер. Сборка и проверка не меняются.

В самих страницах завязок нет. Все ссылки и пути к стилям, скриптам и картинкам
относительные (`guardian.html`, `style.css?v=…`, `img/…`). Сайт работает из корня
любого домена.

**Что GitHub делал за нас и что на своём сервере придётся настроить самим.**
Это не завязки в коде, но без этих настроек canonical и карта будут обещать адреса,
которые сервер отдаёт иначе:

- перенаправление `http://` → `https://` и `www.` → без `www` (или наоборот, но один
  вариант). На GitHub это галочка «Enforce HTTPS» и автоматический `www`;
- GitHub отдаёт `guardian.html` и по адресу `/guardian` без расширения. nginx по умолчанию —
  нет. Canonical в обоих случаях указывает на `.html`, так что поисковику всё равно.
  Но если где-то снаружи уже стоят ссылки без `.html`, на своём сервере они станут 404;
- страницы 404 у нас нет (`404.html`). GitHub показывает свою, nginx — свою, обе голые.
  Это не по этой задаче, просто заметил.
